Lihat 15 penurunan status dan alasannya

full → partial Object type schema definition (typed entities with primary key, enums, API names)

Demoted: ODL syntax and the validator accept an arbitrarily-named @primary field, but no runtime honours it — the column is dropped at packages/api/src/schema-loader.ts:674 and the read path only looks for '_<name>' (resolver-generator.ts:221-223). The PK is always the synthetic system id, so Foundry's 'pick a property as the primary key' is schema-level fiction here; there is also no title-key concept anywhere.

full → partial Property system: base types, required/unique constraints, sensitive fields

Demoted: the 'sensitive fields' third of the claim has no runtime behind it at all (only an unwired SDK generator, packages/odl/src/codegen/sdk.ts:61), and one declared base type (GeoPoint) is storage-provider-dependent — it works in memory and degrades to a TEXT string in Postgres.

full → partial Schema evolution with breaking-change detection and migration gating

Demoted: the report's stated caveat understates it. The boot path does auto-approve by default (schema-registry-boot.ts:86-88; the new 'block' policy only aborts recording, after DDL), and the alternative enforcement route the report credits — 'registry API/CLI' — does not exist: there is no registry HTTP surface, and 'odl apply' writes to a per-invocation in-memory registry (cli/index.ts:175) that is discarded on exit. Separately, evolution itself is blocked at the storage layer by the hardcoded version:1 + checksum-drift throw.

full → partial Ontology-as-code export/edit/import (dump to file, edit, re-import; copy one ontology's state to another)

Demoted: 'gap: None' is refuted on both halves. There is no export (no command or endpoint returns the stored ontology; dump-schema.ts emits SDL regenerated from the same files) and no import (the CLI's apply target is a throwaway object, cli/index.ts:175; the file-drop path fails on checksum drift against a version constant).

full → partial Link types — bidirectional relationships, cardinality, self-links, traversal

The claim's four-item parenthetical is not uniformly satisfied: bidirectional + cardinality are genuinely full, but the traversal side is a one-hop read hardcoded to 1000 rows with no pagination/filter arguments in the generated SDL (codegen/index.ts:127 + resolver-generator.ts:319), the generated SDK exposes no link access at all, and self-links are neither exercised nor coherently handled by the FGA codegen.

full → partial Graph traversal query primitive — search-around equivalent, data layer

Two independent refutations: the production storage provider silently drops `TraversalStep.filter` while the memory provider implements it (traversal.ts:143-158 vs memory-storage-provider.ts:939), and the conformance test that would catch it runs against memory only (memory-provider.test.ts:10) — so the divergence is unguarded; separately the primitive has no caller in any production wiring, so a user of the platform cannot invoke it at all without embedding the engine as a library.

full → partial System graph substrate — the object/link graph scenarios are configured against

The report's own hedge understates it: the AGE graph is not just write-only, it is best-effort write-only (errors swallowed at object-crud.ts:443-449 / link-crud.ts:111-117), property-less, and never read by any code path — so it is genuinely half-dead code that costs a deployment dependency and write amplification while contributing nothing readable. And the report's stated evidence for this row leans on SPI `traverse`, which the Postgres provider implements incorrectly (drops step.filter, traversal.ts:143-158) and which no production caller invokes.

full → partial Action types: declarative create/modify/delete/link rules with parameters, submission criteria, permissions, and side effects

Two of the five bundled sub-capabilities are not deliverable declaratively: there is no delete-object rule in the manifest vocabulary (parser/index.ts:244), and permissions cannot be declared at all — they are derived from the action's name, with a fallback that allows any action lacking an ObjectType param (config.ts:95-101).

full → partial Action side effect: webhooks to external systems

This is not the reported "hardening rather than capability work". Three of the four declarable webhook config fields (url with env placeholder, method, body) are silently ignored, so no user can send a shaped payload to a configured endpoint — the two webhooks that ship in the repo send literal expression strings to an unparseable URL and are reported as successful.

full → partial Governed object/link editing with writeback and external edit APIs

The "editing" verb is incomplete in a way no user can work around without writing platform code: an object can be created, modified and linked through governed APIs but can never be deleted through any of them, and the bulk-edit types exist in the SDL with no resolver behind them.

full → partial Transactional object writeback via Actions with version consistency — edits through actions, read-your-writes, StaleObject/version-conflict detection, edit history retention

"StaleObject/version-conflict detection" is not reachable: the optimistic-concurrency parameter exists only in the storage and engine layers and is supplied by no production caller, and no client-facing API accepts a version to compare against. Two concurrent actions on the same object silently last-write-wins.

full → partial Object sets — saved, shareable, executable object collections with aggregations

Saved+executable+aggregable is genuinely delivered, but 'shareable' is a single public/private boolean with no grants, execution exists only on REST (the generated GraphQL contract can save a set it cannot run), and the execute path bypasses the field-visibility predicate check the sibling list and aggregate paths enforce.

full → partial Object and property security policies — row-, column-, and cell-level security

Two of the three named levels hold; the third does not exist at all. Field visibility cannot vary per row anywhere in the code, so 'cell-level security' has no implementation — and column-level itself fails open for any object type without a pack-supplied field-permissions.yaml.

full → partial Object edit history and temporal queries

The 'edit history' half is confirmed; the 'temporal queries' half is unreachable code — point-in-time reads exist only as an SPI method with no production caller, and the asOfVersion/asOfTime query options are a dead type.

full → partial Grouped aggregation / pivot backend over object sets

Grouped aggregation over stored scalar fields is genuine and provider-symmetric, but a whole field class (computed/derived) fails divergently and silently across the two providers, the GraphQL surface cannot order or paginate groups, and aggregates skip the consent gate the other read paths enforce.

Ontology core

8 · 7 · 5

Altius has a genuinely strong kernel equivalent for this theme: typed object/link/property schema definition (ODL), governed actions with submission-criteria-style CEL preconditions and per-action permissions, row/column/cell-level security, object sets, version history, and best-in-class schema-change classification (SAFE/COMPATIBLE/BREAKING with migration gating). The single most impactful gap is the logic layer: Foundry's Functions (FOO, function-backed actions, derived-property functions, custom aggregations) has no Altius counterpart beyond a CEL expression sidecar and a one-builtin computed-field evaluator, which blocks the entire class of code-driven derivations and complex action logic; branching/proposal review, structs/shared properties, media, and all UI-facing ontology metadata are also absent.

Data pipelines

0 · 5 · 8

Altius has essentially no data-pipeline layer: Foundry's core substrate here — versioned/transactional datasets, batch transform frameworks, Pipeline Builder, ad-hoc SQL, projections, and the Foundry Rules batch rules engine — is absent, because Altius stores ontology objects directly in per-type Postgres tables and mutates them only through governed per-request actions. The one real primitive is packages/sync (JDBC connector, mapping DSL, CDC consumer, conflict resolver), but it is a library of unwired components with no scheduler, no Debezium intake code, and no production ChangeApplier. The single most impactful gap is the missing batch compute substrate (dataset primitive + transform execution + scheduling), on which every other capability in this theme depends; the partial credits (temporal/history reads, ODL-generated indexes, CDM export, record-level CEL validation) are per-record ontology mechanisms, not pipeline mechanisms.

absentVersioned transactional dataset primitive (datasets as branchable, transaction-log-backed tabular resources)

Evidence (Altius)

none — Altius has no dataset/file abstraction at all. Storage is one Postgres table per ObjectType plus <type>_history snapshot tables (packages/storage-postgres ddl-objects.ts); no transactions-as-data-versions, no branches anywhere in the system.

Gap

Greenfield. Would require a whole new storage subsystem (file/tabular store + transaction log + branching); nothing in the SPI contract (packages/spi/src/storage-provider.ts) is dataset-shaped. Arguably out of scope for a headless ontology platform, but every other capability in this theme presumes it.

absentDataset REST API (metadata + schema retrieval addressed by branch / transaction / schema version)

Evidence (Altius)

none for datasets. Closest schema-introspection surfaces: GET /api/v1/openapi.json (generated contract), GET /admin/packs (pack/type counts, unauthenticated), spec/dump-schema.ts SDL dump, and the ODL schema registry versions in PostgresSchemaRegistry (packages/storage-postgres) — none addressable by branch/transaction.

Gap

A read-only 'schema version N' endpoint over PostgresSchemaRegistry would be a small addition (the registry already stores versioned ParsedSchema snapshots with diff/classify); branch/transaction addressing has no substrate.

absentCode-based batch transform framework (transforms-python / Java transforms on Spark, incremental transforms)

Evidence (Altius)

none — no transform execution framework, no job runner, and explicitly no scheduler anywhere (architecture map: 'no scheduler exists anywhere in packages/sync'; SyncConfig.interval parsed but never consumed). The only transform-like code is packages/sync/src/mapping's per-record, single-call string transform DSL (trim/toUpper/concat/custom), which is record mapping, not dataset compute.

Gap

Greenfield: needs a batch engine + scheduler + dataset IO. The sync mapping DSL is the only hook and is deliberately record-scoped; nothing to extend into Spark-class batch compute.

absentProgrammatic tabular read/write SDK (foundry.transforms.Dataset: pandas/polars/arrow IO with filter pushdown, schema inference, file upload)

Evidence (Altius)

none — the generated TypeScript SDK (packages/odl/src/codegen/sdk.ts targeting packages/sdk-typescript) is a transport-less GraphQL API client whose query/mutate/subscribe throw 'Not implemented' and whose list() ignores filters/pagination; it is record-API-shaped, not dataframe-IO-shaped. No bulk tabular read path exists beyond the 10k-row CDM export.

Gap

Even the API-client SDK is unwired (no generate-to-publish step, no runtime transport). A dataframe/bulk-IO SDK would additionally need a bulk read/export surface the API layer does not have (consent-aware pagination hard-caps scans at 10,000 rows).

absentNo-code pipeline authoring with configurable dataset outputs (Pipeline Builder: output schema mapping, write modes, file formats)

Evidence (Altius)

none for pipelines/outputs. The only declarative-mapping analog is pack connector YAML (domain-packs/*/connectors/*.yaml parsed by packages/sync/src/mapping/mapping-parser.ts): datasource → object mapping with transform expressions and a sync block — ingestion-direction only, no outputs, no write-mode semantics, no builds.

Gap

Write-mode semantics (dedupe by primary key, changelog, snapshot-replace) have no home without a dataset primitive; the mapping YAML could grow richer transforms cheaply, but the output/build half is greenfield.

partialData expectations / quality checks that gate builds

Evidence (Altius)

Record-level write-time validation exists and is real: packages/engine validation.ts (schema/type/uniqueness CQ-01 checks, severity model where unevaluable constraints downgrade to warnings) plus CEL constraint evaluation via the packages/cel-evaluator Go sidecar in the 8-stage action pipeline (validate stage), and DB-level backstops (unique/cardinality indexes in storage-postgres DDL).

Gap

The Foundry feature is batch/dataset-level (assert over a whole output before publishing); Altius only validates individual records at write time. No batch context exists to attach expectations to; also inline CEL fallback downgrades unevaluable constraints to warnings, and URI-based JSON-schema validation is fail-open (no schema registry yet).

absentInteractive SQL query service (Spark SQL REST API with async job lifecycle)

Evidence (Altius)

none — no ad-hoc SQL surface and no async query-job model. Closest: the generated structured query surface per ObjectType (GraphQL foos/fooAggregate/searchFoos and REST /api/v1/{plural} list/aggregate/search via packages/api resolver-generator + rest/route-generator, backed by SPI queryObjects/aggregateObjects/searchObjects). Postgres SQL exists internally but is never exposed.

Gap

Exposing governed ad-hoc SQL would have to replicate the whole security pipeline (FGA listObjects scoping, field redaction SEC-14 predicate-leakage rules, consent filtering) inside a SQL planner — the existing per-field authorization design actively resists arbitrary SQL. Async job lifecycle is also greenfield (all Altius queries are synchronous request/response).

partialOntology materializations and governed bulk export (latest object state incl. user edits exported to datasets/restricted views)

Evidence (Altius)

The latest object state (including all action edits) natively lives in one Postgres table per ObjectType (packages/storage-postgres, snake_type tables) — the 'materialized latest state' exists by construction rather than by pipeline. Governed bulk export exists narrowly: GET /api/v1/cdm/{SourceType}/export?format=ndjson|csv with FGA + field redaction + consent, capped at 10,000 rows with truncation headers (packages/api/src/cdm/router.ts, capability-gated on the cdm pack flag).

Gap

No propagation machinery is needed for the tables themselves, but reading them directly bypasses all governance (redaction/consent are API-layer, RLS explicitly deferred post-MVP per ddl-consent.ts) — so there is no governed dataset-shaped export beyond the 10k-row CDM path, no restricted-view equivalent, and no marking-provenance propagation. Raising the export path to a first-class, uncapped, per-type governed export is the realistic close.

partialDataset projections / query acceleration (filter- and join-optimized projections, incremental compaction, transparent planner use)

Evidence (Altius)

The Postgres-native analog is declarative index generation: ODL IndexDefinitions emit CREATE INDEX DDL per ObjectType (packages/storage-postgres ddl-objects.ts — BTREE plus GIN to_tsvector for FULLTEXT), tenant-scoped unique indexes, and partial unique indexes for cardinality; the DB planner uses them transparently, which covers the filter-acceleration use case for OLTP-scale data.

Gap

Known defect-shaped gap: the FULLTEXT tsvector GIN index is generated but never used — runtime searchObjects issues ILIKE '%q%' with CASE-WHEN scoring, so search does not scale (fix is a real tsquery path in objects/search). Join/aggregation bucketing and file compaction are Spark-world concepts with no Altius counterpart and none needed at current scale.

absentFoundry Rules: no-code batch rules engine over the ontology (rule authoring + governed rule outputs + generated rules pipeline)

Evidence (Altius)

none as a batch capability. The related primitives are per-request, not batch: YAML action manifests with CEL preconditions + declarative effects (packages/actions parser + ActionExecutor 8-stage pipeline) and the packages/cel-evaluator Go sidecar (canonical CEL runtime with has_link/count_links/hasRole custom functions).

Gap

A 'rules' capability would need: a rule registry (schema exists for nothing like it), a batch evaluator that sweeps object populations through CEL (the sidecar evaluates one context per call today, with eagerly pre-resolved _links), an outcome-staging concept (action-ready proposals rather than immediate execution), and authoring governance like permitted/default values. The CEL sidecar is a genuine reusable foundation; everything else is greenfield.

partialSource-system sync / CDC ingestion with edit-vs-source reconciliation

Evidence (Altius)

This is Altius's strongest theme entry: packages/sync implements connectors (JdbcConnector with fullExtract/incrementalExtract updated_at polling; REST stubbed), YAML datasource mapping with compiled transform expressions, CdcConsumer with CheckpointStore (checkpoint every 100 records), ConflictResolver (LAST_WRITE_WINS / SOURCE_PRIORITY / ACTION_PRIORITY protecting action-written fields), OverlayEngine (read-through TTL cache), and an in-memory QuarantineQueue; deploy/docker-compose ships Debezium 2.7.3 + Redpanda.

Gap

Componentized but not a running pipeline: no scheduler/driver loop (SyncConfig.interval parsed, never consumed), no code consumes Kafka/Debezium envelopes (CdcConsumer input is AsyncIterable<SourceRecord> from polling), no production CheckpointStore/IdentityStore implementations (test doubles only), the ChangeApplier seam is unimplemented host-side (packages/api only validates connector manifests at boot), ACTION_PRIORITY's 'action:' source prefix has no producer, and synced writes bypass the action pipeline by design. Hooks all exist; wiring + a scheduler is the work.

partialSchema and data version time-travel (schema at any version; reads as of version/time; historical snapshots)

Evidence (Altius)

Working equivalents at ontology granularity: per-type *_history tables written in the same transaction as every create/update/soft-delete, powering SPI getObjectAtVersion/getObjectAtTime and QueryOptions.asOfVersion/asOfTime (packages/storage-postgres temporal-queries.ts); REST GET /api/v1/{plural}/:id/history; ODL schema versions durably stored in PostgresSchemaRegistry with SAFE/COMPATIBLE/BREAKING diff classification and reverseDiff rollback (packages/odl diff/classify).

Gap

No branches, and no bulk 'dataset as of T' read — time-travel is per-object only (engine managers expose no time-travel API; it lives below in the SPI). Schema-evolution enforcement is soft at boot: recordSchemaVersion auto-approves BREAKING changes with a warning (real gating only via SchemaRegistry.applySchema). LineageStore is in-memory only.

absentNo-code client-side variable transformations (Workshop derived values: string/math/date/object-set/geospatial/array operations)

Evidence (Altius)

none — Altius is headless with no UI/variable layer by scope. Server-side fragments that cover slivers: GraphQL fooAggregate (COUNT/SUM/AVG/MIN/MAX + groupBy) via resolver-generator, and the engine's ComputedFieldEvaluator with exactly one builtin (countLinks) and LAZY cache only.

Gap

Out of scope for a headless platform (a client app would own this). The nearest server-side investment with leverage is expanding ComputedFieldEvaluator builtins / derived properties, which is an acknowledged MVP shim.

Analytics & time series

Altius has a solid headless structured-query substrate — grouped aggregations, composable filters, full-text search, saved object sets, multi-hop graph traversal, and per-object temporal history — but essentially none of Foundry's analytics layer proper: no time series subsystem (no TS property type, no transform/summarizer engine, no interval-detection rules) and no analysis/visualization surface (Quiver, Vertex, Workshop analysis widgets). Scenarios & simulation

1 · 4 · 6

Scenario/simulation is a wholly missing pillar in Altius: parity is near-zero on everything simulation-specific (no what-if sandbox, no scenario persistence, no model registry/inference, no chained orchestration, no UI), while the substrate Foundry builds scenarios on is largely present (governed transactional actions with CEL, graph traversal, temporal as-of reads, pack-based packaging). The single most impactful gap is the absence of any hypothetical-execution/branching mechanism — every action writes immediately to the live ontology, so there is nothing to stage, compare, save, or apply; the SPI Transaction contract plus the existing *_history temporal tables are the natural hooks for building one.

absentWhat-if scenario simulation (create scenario, override model inputs, run, compare against auto-run baseline)

Evidence (Altius)

none — no sandbox/branch/hypothetical-execution mode anywhere; packages/engine ObjectManager/LinkManager and packages/actions ActionExecutor always write to live storage through the SPI

Gap

Entire simulation layer is greenfield. Nearest hooks: SPI Transaction contract (packages/spi/src/storage-provider.ts) could host a run-and-rollback dry-run mode cheaply, and *_history temporal tables give as-of reads, but there is no scenario container, no input-override mechanism, no baseline comparison.

partialScenario staging and transactional apply (hold a set of Actions un-applied, then apply all-or-nothing to the Ontology, gated by an apply-Action's permissions)

Evidence (Altius)

The transactional-apply half exists: packages/spi Transaction (beginTransaction/commit/rollback), ActionExecutor's 8-stage pipeline commits all effects of one action atomically with compensating-transaction rollback for side-effects (packages/actions/src/action-executor.ts); authorize/consent stages give governed gating equivalent to the apply-Action permission check.

Gap

No deferred/staged execution: actions run immediately, there is no buffer holding N pending actions for a later batch apply, and bulkMutate is explicitly non-transactional (storage-postgres bulkMutate: sequential, partial-failure). Needs a scenario/changeset store plus a multi-action transactional apply path — moderate effort on top of the existing Transaction SPI.

absentScenario persistence and sharing as Ontology objects (scenario trait, typeclasses, save/load via Actions and object sets)

Evidence (Altius)

none for scenario state; the closest pattern is the saved-object-set store — ObjectSetManager with REST /api/v1/object-sets CRUD + execute/aggregate and GraphQL objectSet mutations (packages/engine object-set manager, storage-postgres/src/object-sets/postgres-object-set-store.ts) — which persists saved queries, not hypothetical world-states

Gap

No scenario object kind, no versioned scenario RID, nothing to persist because scenarios don't exist. Once a scenario/changeset primitive exists, the object-set store and ODL typeclass-free schema could model it, but today it is greenfield.

absentML model asset registry and lifecycle (model artifacts + adapters, version history, permissioning, lineage, Modeling Objectives review/release)

Evidence (Altius)

none — no model registry, no artifact storage, no adapter concept anywhere in the maps; the only versioned-registry machinery is the ODL schema registry (packages/odl registry + storage-postgres PostgresSchemaRegistry), which versions schemas, not models

Gap

Whole ML platform pillar missing and out of current scope (headless ontology platform). The schema-registry pattern (versioning, advisory-locked applies, migration gating) is a proven template if a model registry were ever built, but everything model-specific is greenfield.

absentModel inference execution (no-code live deployments, batch inference, inference history)

Evidence (Altius)

none — no inference runtime; only outbound-call primitives exist: webhook side-effects via injected HttpClient fetch (packages/actions side-effect-executor, wired in packages/api/src/server.ts) and a stubbed REST connector in packages/sync

Gap

Could be approximated short-term by webhook side-effects calling an externally hosted model, but there is no model invocation contract, no result capture into the ontology, no inference history. Greenfield.

absentChained model orchestration (auto-propagate one model's outputs as the next model's inputs across a multi-model case study)

Evidence (Altius)

none — no DAG/orchestration engine and no scheduler anywhere (packages/sync explicitly has no driver loop; SyncConfig.interval parsed but never consumed); action side-effects are flat post-commit lists, not chained computations

Gap

Requires both a model-invocation layer (absent, see inference) and a dependency-graph executor (absent). Note Foundry itself sunset this in favor of composing function-backed Actions — the Altius-shaped equivalent would be action chaining, which also does not exist today.

partialBusiness logic as ontology-bound functions (Functions on models published as function-backed Actions, the recommended scenario logic path)

Evidence (Altius)

Declarative governed logic exists: YAML action manifests with CEL preconditions and effect expressions executed by ActionExecutor (packages/actions), with the Go cel-evaluator gRPC sidecar (packages/cel-evaluator, cel-go + custom functions has_link/count_links/hasRole/validateJsonSchema) as the canonical expression runtime.

Gap

No user-authored code runtime: logic is limited to CEL expressions plus declarative set/create/link effects (effect values use a separate mini-DSL, resolveExpression). Arbitrary function authoring, a function registry, and function-backed action execution are greenfield; the manifest/executor seam is the natural extension point.

partialTime series as simulation inputs/outputs (time window selection, smoothing, live polling, historic vs predicted comparison)

Evidence (Altius)

Temporal object history only: per-type *_history snapshot tables power getObjectAtVersion/getObjectAtTime and QueryOptions.asOfVersion/asOfTime (packages/storage-postgres temporal-queries.ts, SPI contract in packages/spi); REST GET /api/v1/{plural}/:id/history exposes version history.

Gap

History-of-object-state is not a time-series store: no time-series property type in ODL, no windowed/smoothing/resampling queries, no live polling, no series-valued model I/O. A real time-series capability is a significant storage + query + schema extension.

The graph data layer is real and working: SPI traverse with TraversalPath/Options, SQL-join traversal with depth (10) and node (10k) guards (packages/storage-postgres/src/links/traversal.ts, storage-memory equivalent), Apache AGE graph maintained write-side, link tables per LinkType, and per-link nested GraphQL field resolvers with FGA re-checks (packages/api resolver-generator).

Gap

None at the data layer. The visual/system-graph document (saved graphs, node display, scope-to-graph filtering) is UI and covered under the UI-tooling row.

absentScenario and graph UI tooling (Vertex canvas, scenario pane, Workshop scenario widgets/variables/buttons, Control Panel admin settings)

Evidence (Altius)

none — Altius is explicitly headless (no UI layer); the only admin-ish surfaces are GET /admin/packs introspection and env/Helm deployment configuration (packages/api/src/server.ts, Orion/helm chart)

Gap

By design, not an oversight: Altius's generated GraphQL/REST/SDK surface is the substrate a UI would sit on. Runtime admin settings (Foundry Control Panel analogue) are also absent — all platform tuning is boot-time env vars, no settings API.

partialPackaging and distribution of reusable artifacts (Vertex graph templates in Marketplace products via DevOps)

Evidence (Altius)

Domain packs are a working packaging/distribution mechanism: pack.yaml manifests bundling ODL schema, action manifests, .fga permission overrides, field permissions, connectors, and seeds, loaded from DOMAIN_PACKS_EXTRA_DIRS external dirs (read-only mounts), with version + '>=' dependency checks and /admin/packs + Prometheus pack-loaded introspection (packages/api/src/schema-loader.ts, docs/external-domain-packs.md).

Gap

Packs distribute ontology/logic/security artifacts but there are no template-like artifact kinds (graphs, scenarios, dashboards) to package, and no marketplace/store/install UX — distribution is filesystem mounts, not a catalog. Extending pack.yaml with new artifact kinds is easy; a marketplace is greenfield.

Security & governance

0 · 7 · 5

Altius and Foundry solve security with different paradigms: Foundry's governance centerpiece in this doc set is mandatory access control (Markings) propagating along data lineage, while Altius ships a genuinely working discretionary/relationship stack (OpenFGA ReBAC, field-level redaction, consent, audit) with zero mandatory-control constructs. The single most impactful gap is the complete absence of a data-classification/marking layer (labels, conjunctive membership checks, lineage propagation, scoped sessions) — mitigated only by the fact that Altius's one shared authenticate→FGA→redact→consent pipeline gives a clean single insertion point to add it.

absentMarkings: mandatory access-control labels with centralized administration

Evidence (Altius)

none — no marking/label construct anywhere; closest primitives are discretionary: OpenFGA relations (packages/odl generateOpenFGASchema, packages/security AuthorizationService) and field permissions (permissions/field-permissions.yaml)

Gap

Greenfield: needs a label store, user-membership grants, and a conjunctive check inserted into the read path. A clean hook exists — every surface funnels through one authenticate→FGA→redact→consent pipeline (packages/api/src/graphql/resolver-generator.ts, rest/route-generator.ts) — but the OpenFGA generator emits union-based models only; marking semantics need intersection, so this is a new subsystem, not a config change.

absentMarking propagation along data lineage (inheritance, simulation, stop_propagating)

Evidence (Altius)

Lineage primitives only: engine LineageRecorder (in-memory only, explicitly outside the SPI), lineage.field_provenance Postgres schema, FieldProvenance/ProvenanceSource SPI types. Nothing propagates security metadata.

Gap

Doubly greenfield: no marking construct to propagate, and no transform/pipeline layer to propagate through (Altius's only data-in path is sync ingestion, itself not wired end-to-end). The durable lineage store would also need building — LineageStore is an in-memory MVP shim.

absentScoped sessions (session-restricted marking subsets)

Evidence (Altius)

none — auth is stateless per-request OIDC JWT (packages/security/src/auth/oidc-authenticator.ts); no session or scoping construct

Gap

Greenfield and only meaningful after markings exist; would need a session-scoping claim honored by the shared authz pipeline. Low priority until capability 1 lands.

partialSensitive-data (PII) protection controls

Evidence (Altius)

Working field-level machinery: @sensitive ODL directive (SDK emits T | Redacted with REDACTED symbol), permissions/field-permissions.yaml → FieldPermissionConfig → AuthorizationService redaction (visible = alwaysVisible ∪ fieldsByRelation, additive), _redactedFields/_consentRestricted on every object, SEC-14/SEC-14b blocking filter/orderBy/search/aggregate over hidden fields (predicate-leakage prevention), consent restriction nulling non-primary fields; FGA listObjects hides unauthorized objects entirely.

Gap

Mechanism is discretionary and role/relationship-derived — there is no mandatory, category-based control a DPO can centrally grant/audit ('who may ever see PII'), and redaction config is per-pack YAML, not centrally administered. Field redaction is production-real; the missing half is the mandatory layer (capability 1).

partialLayered permission separation (app/module vs data vs action vs function)

Evidence (Altius)

The data-side layers all exist independently: per-object FGA viewer checks on every surface (REST/GraphQL/FHIR/CDM/subscriptions), per-action can_* relations via actionPermissionRelation (packages/odl, single source of truth per commit 1349877), field visibility via FieldPermissionConfig, consent as an independent step — each enforced separately in the pipeline.

Gap

No module/app permission layer because Altius is headless by design (no UI artifacts to permission), and no function-level permissioning (no user-facing function resource; CEL sidecar is internal). The data/action/field separation is at parity; the app half is out of scope until a UI layer exists.

partialProject-hierarchy permission inheritance and ontology-resource governance

Evidence (Altius)

Ontology-change governance exists but is git/registry-shaped, not hierarchy-shaped: odl diff/classify (SAFE/COMPATIBLE/BREAKING), MigrationPlan-gated applySchema, PostgresSchemaRegistry (versioned JSONB snapshots, advisory lock 0x5352), odl CLI apply/rollback; packs are filesystem artifacts governed by repo access.

Gap

No runtime permission hierarchy over schema resources (no projects/folders/roles on object types) — pack files in git are the de facto ACL. Also the boot path auto-approves BREAKING changes ('Recorded at server boot'), so registry gating is advisory in practice; a governance-time schema-management API is documented as future work. Closing this fully means a resource-catalog service — large; hardening boot gating is small.

absentPermission checking / access-explanation tooling

Evidence (Altius)

No explain/why surface. Internal hooks only: AuthorizationService.check/listObjects, boot-time assertFgaModelCoverage validation, and the hand-rolled fga-dsl-to-json parser in packages/api/src/server.ts that already understands the merged model.

Gap

Moderate-effort feature on existing primitives: an endpoint composing FGA check/expand + field-permission + consent evaluation for a target user would reuse the whole existing stack; OpenFGA's expand API is unused. Greenfield only in the API/UX sense, not in mechanism.

partialApproval/proposal workflows with attribute-based submission criteria

Evidence (Altius)

The enforcement primitive exists and works: CEL preconditions in the 8-stage action pipeline (packages/actions ActionExecutor + packages/cel-evaluator Go sidecar) support actor.hasRole/hasPermission, object-attribute comparisons, and has_link — exactly the 'actor == object.author OR superuser' pattern; denials are audited via auditDenied.

Gap

No shipped proposal/approval object model or review workflow — a domain pack would have to model Proposal objects plus approve/reject actions itself (feasible today with existing ODL + manifest machinery, but nothing is provided out of the box).

partialAI/agent write governance (human-approved, non-destructive agent access)

Evidence (Altius)

The core governance property — agents can only act through governed actions — has a substrate: tool-registry.ts (packages/actions) derives LLM tool descriptors from action manifests, ToolKind/ToolDescriptor/ToolFilter are in the generated GraphQL SDL, and any tool invocation runs the full 8-stage pipeline (validate→authorize→consent→preconditions→execute→side-effects→audit→emit). Pilot scenario 7.9 covers the AI tool registry.

Gap

No MCP server, no LLM/agent layer at all (stated platform gap), and no human-approval proposal gate for agent-initiated changes — the tool registry is descriptors-only today. The pipeline guarantees are real; the agent-facing surface and review workflow are greenfield.

absentCheckpoints: justification capture for sensitive actions

Evidence (Altius)

Audit trail exists (AuditWriter → audit.audit_records with OTel traceId; auditDenied for refusals) but nothing prompts for or stores a user justification, and there is no checkpoint configuration or review surface.

Gap

Small-to-moderate: a required 'justification' action param plus audit-detail capture could be declared per-manifest today with zero engine changes; a reusable checkpoint framework (config, enforcement across surfaces, review UI) is greenfield.

partialAccess-decision audit trail (DPO auditability)

Evidence (Altius)

Systematic auditing: every action audited post-commit, authz/consent denials audited (auditDenied), relationship grants/revokes and consent writes/denials audited (relationships/router.ts, consent/router.ts), AuditWriter → audit.audit_records with trace correlation, AuditStore query interface (AuditQueryFilter, audit-query module, PostgresAuditStore).

Gap

Append-only is application-level only (ddl-audit.ts has no REVOKE/GRANT despite the interface doc claiming it), audit writes are best-effort post-commit, and there is no API/UI surface exposing audit queries — the query interface exists but is not mounted as a route. Hardening + one endpoint away from solid.

partialOrganization/tenant boundary isolation

Evidence (Altius)

Row-level multi-tenancy enforced everywhere: _tenant_id composite PKs and tenant-scoped unique indexes (storage-postgres), RequestContext.tenantId threaded through every SPI call, fail-closed 401 on missing tenant claim unless OIDC_DEFAULT_TENANT opts in, tenant-scoped idempotency and rate limits.

Gap

Isolation is app-layer only — Postgres RLS is explicitly deferred post-MVP (documented in consent DDL), so a query-construction bug bypasses tenancy; and there are no cross-org collaboration/sharing constructs (Foundry's org-restricted categories, cross-org projects). RLS is a bounded hardening task; cross-org sharing is greenfield.

Greenfield agent layer. The invocation substrate (governed actions via POST /api/v1/actions/{Name}, tool descriptors) exists, so an external agent framework could be wired against the API today, but Altius ships no in-platform equivalent.

partialUniform governance of AI actors (agents under same security/audit as humans)

partialNo-code business rules over data (Foundry Rules logic)

absentEmbedded AI copilots across platform applications

Platform ops

1 · 7 · 5

Platform-ops parity is low-to-moderate: Altius covers the developer-facing halves well (pack-based product packaging, declarative action rules, webhook side effects, CloudEvents emission, Helm-based delivery, infra monitoring) but has nothing above the action pipeline — no scheduler, no trigger/automation engine consuming its own event bus, no end-user rule authoring, and no UI-layer features at all. absentNo-code end-user rule authoring with proposal/approval workflow and generated execution pipeline (Foundry Rules)

partialDeclarative action logic (ontology-edit rules)

Also no create-or-modify upsert rule, no interface-targeted rules, and undo/revert exists in the manifest schema but is unexercised (all built-in packs ship reversible:false). Gap

fullAction side effect: webhooks to external systems

absentAction-triggered scheduled builds (Schedule rule)

none — Altius has no build system, no pipelines, no transforms, and no scheduler anywhere (packages/sync explicitly has no driver loop; SyncConfig.interval is parsed but never consumed).

partialEvent-driven automation / condition-triggered logic (Automate, successor to Object Monitors)

Evidence (Altius)

absentWorkshop application UI runtime features (widget event system, URL routing/shareable state, module changelog & rebase)

none — Altius is headless by design (no UI layer at all). partialVersioned change management with diff, classification, and rollback

Evidence (Altius)

For the ontology schema this is fully built: packages/odl diff/classify (SAFE/COMPATIBLE/BREAKING), reverseDiff for rollback classification, InMemorySchemaRegistry + PostgresSchemaRegistry (_schema_registry JSONB snapshots under advisory lock 0x5352), BREAKING applies refused without an approved MigrationPlan, and the odl CLI (validate/diff/apply/rollback).
